## Assets

| Asset | Where | Primary protection |
|---|---|---|
| Escrowed funds | `VeriPayEscrow` | Contract rules; no admin withdrawal path |
| Buyer's pre-lock balance | Buyer's own EOA | Passkey-derived key on device |
| Seller payouts | Seller's EOA | Passkey-derived key on device |
| Seller identity (handle → address) | `sellers` table | EIP-191 signature proof |
| Payment integrity (charge ↔ mint) | `pay_intents` | Server-side Paystack verification, SQL guards |
| Minter / gas wallet | Server env | Secret management; caps on spend |
| Reputation integrity | Contract events | Event-sourcing; no editable store |
| User data (emails, chat) | Supabase | RLS with no policies; service-role only on server |

<Accordion title="In plain words" icon="lightbulb">
  These are the things worth protecting — mainly the money in the safe, but also the link between a shop and its account, the honesty of seller records, and personal data like emails and messages — and what keeps each one safe.
</Accordion>

## Principles

<CardGroup cols={2}>
  <Card title="Custody by code, not company" icon="vault">
    The escrow has no owner path to customer funds. VeriPay's compromise can't drain locked orders.
  </Card>
  <Card title="Verify, don't trust, the browser" icon="shield-alert">
    Amounts, prices, payout addresses and payment success are decided server-side or on-chain.
  </Card>
  <Card title="Atomic state transitions" icon="lock">
    Every value-moving DB transition is a compare-and-swap in SQL; contract state flips before transfers.
  </Card>
  <Card title="Least privilege" icon="key">
    Each key holds exactly the power it needs; caps bound worst-case loss.
  </Card>
  <Card title="Fail safe, degrade gracefully" icon="life-buoy">
    Dependency outages slow things down; they don't unlock funds.
  </Card>
  <Card title="Transparent by default" icon="eye">
    Proof page, public events, open-source code, honest status disclosures.
  </Card>
</CardGroup>

## Defence summary

| Threat | Defence | Where |
|---|---|---|
| Browser lies about a card payment, or pays less | Server verifies status, currency and amount with Paystack directly | `src/lib/paystack.ts` |
| One payment reused for another order | Reference generated server-side and bound to one intent; `UNIQUE(paystack_ref)` | `src/lib/payments.ts` |
| Double-click or race delivers twice | Status guard in SQL `WHERE`; single delivery slot | `src/lib/payments.ts` |
| Someone registers a link that pays another account | Claim must be signed by that account; verified server-side | `src/lib/sellers.ts` |
| VeriPay (the owner) takes customers' money | No such function; `withdrawFees` moves only fees | `contracts/VeriPayEscrow.sol` |
| Fee raised on orders already placed | Fee rate stored per order at creation | `contracts/VeriPayEscrow.sol` |
| Fee raised without limit | `MAX_FEE_BPS = 500` constant | `contracts/VeriPayEscrow.sol` |
| Forged auto-release report | Receiver accepts reports only from the configured forwarder | `contracts/cre/ReceiverTemplate.sol` |
| Gas sponsorship farmed as a faucet | Eligibility; cap 3; counted before sending | `src/lib/payments.ts` |
| Token returning `false` instead of reverting | Every ERC-20 transfer wrapped in `require` | `contracts/VeriPayEscrow.sol` |
| Reentrancy via token/recipient | `nonReentrant`; flags set before transfers | `contracts/VeriPayEscrow.sol` |
| Database read by the public | RLS on every table, no public policies | `supabase/schema.sql` |
| Tampered exchange price | Server-side pricing; client sends intent only | `src/lib/pricing.ts` |
| Fake sell-side deposit | On-chain verification of to/from/value/status; unique tx hash | `src/lib/chainVerify.ts` |
| Forged Paystack webhook | HMAC-SHA512 signature check | `src/lib/paystack.ts` |
| Phishing for credentials | Passkeys are origin-bound | WebAuthn |
| Stale cached financial data | Service worker never caches `/api/*` | `public/sw.js` |
