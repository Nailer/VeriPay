<Warning>
  **VeriPay's contracts have not been independently audited.** Do not put meaningful real money through them until they are.
</Warning>

<Accordion title="In plain words" icon="lightbulb">
  No outside security company has checked VeriPay's code yet. It has been tested a lot by the founder, but that's not the same thing. An independent review is the first thing to do before real money.
</Accordion>

## What has been done

| Verification | Scope | Result |
|---|---|---|
| Local-EVM test suite | `VeriPayEscrow` (23), `AutoReleaseReceiver` (7) | 30/30 passing |
| End-to-end money path | Card → verify → mint → gas → lock → reputation, plus fraud attempts | 14/14 locally and on the live deployment |
| On-chain configuration read-back | owner, arbitrator, feeRecipient, feeBps, autoReleaseDelay | Matches intended values |
| Chainlink template | Vendored verbatim from Chainlink | Not modified |
| Indexer vs chain parity | Every address that has traded | Identical numbers |
| Real auto-release | Order #2 via CRE | Succeeded on-chain |

## What has not been done

- Independent manual audit.
- Formal verification or invariant/fuzz testing.
- Penetration test of the web app and API.
- Review of key management and operational security.
- Economic review of dispute incentives and wash-trading resistance.

## Plan

<Steps>
  <Step title="Pre-audit hardening">Fix known limitations (refund-approved auto-release, pull-payment fallback, API auth gaps, admin passcode default), add invariant tests.</Step>
  <Step title="Independent audit">Scope: `VeriPayEscrow.sol`, `AutoReleaseReceiver.sol`; off-chain money path (`payments.ts`, `paystack.ts`, `sellers.ts`).</Step>
  <Step title="Fix and re-review">Publish the report and fixes.</Step>
  <Step title="Mainnet with limits">Per-order caps and monitoring at launch.</Step>
</Steps>

Budget for this is part of the pre-seed plan — see [Roadmap](/resources/roadmap).
